# CGPRR NEET AI — Design note

## Scope and architecture
This prototype demonstrates NEET.info-style counselling using **only fictional synthetic admission records**. It is not a real college finder. Eight invented institutions and 64 invented cutoff rows are supplied. The frontend talks to FastAPI. The /predict route reads CSV and deterministically filters state, course, category, quota and year, then checks `rank <= fictional closing_rank`. /chat first checks explicit filters; fully specified closing-rank requests are resolved exactly from the CSV. Other queries are embedded locally with FastEmbed `BAAI/bge-small-en-v1.5` and searched in Qdrant (cosine similarity, default threshold 0.48). The top retrieved records are sent to a Qwen2.5 3B Instruct open-weight GGUF model running in LM Studio at localhost:1234. The generation prompt requires source IDs; answers lacking a citation from the retrieved set are refused. An exact lookup avoids LLM numerical hallucination. This is not a formal entailment verifier: a model could still make incorrect statements using a valid citation.

## Local deployment and model/hardware assumptions
Development target: Apple MacBook Air M1, 8 GB unified memory; use quantized Qwen2.5 3B Instruct (Q4 GGUF) in LM Studio, with CPU embedding model to avoid simultaneously loading a second embedding model into the LM Studio runtime. Model download requires internet once; subsequent inference is local. Target office deployment assumption: **RTX 6000 Ada, 48 GB VRAM**, a single GPU, not a multi-GPU cluster. Rough model weights: 3B at 4 bits ≈ 1.5 GB raw; quantization metadata, KV cache, activations and runtime overhead require more; plan approximately 3–6 GB VRAM for this small model depending on context/concurrency. Embeddings can remain CPU-bound. This leaves substantial VRAM headroom but should be measured on the actual card. No GPU throughput was measured for this assignment; a cautious initial expectation is tens of generated tokens per second at a single request, but real performance must be benchmarked. CPU/unified-memory speed will differ.

## Data handling, isolation, logging
CSV is stored under `data/`; vector payloads live in a local Qdrant Docker volume and the embedding cache in a Docker volume (or user's Hugging Face cache for native Python). The application doesn't intentionally send the dataset to paid cloud LLM services. **First-time model downloads do contact public model repositories**. LM Studio local networking and its update behavior should be configured for organizational requirements. Development app logs go to terminal / Docker logs and may include operational errors, not intentionally full private documents; production should prohibit sensitive prompt logging and implement log retention. For multiple businesses, deploy separate Qdrant collections or instances, access controls, encryption at rest, and business-scoped credentials; do not share NEET, Hirrx or editorial source records by default. API currently has no authentication and should run only on localhost; it must not be exposed publicly.

## Evaluation, limitations and approximate cost
16 predefined cases: deterministic sourced ranks, unsupported years and quotas, ambiguous questions, injection-like user text, two local-LLM summaries, and predictor matching/empty cases. `python scripts/evaluate.py` checks 14 non-live cases; `--live` indexes, tests both LM Studio summaries and writes CSV results. The tests are simple behavioral checks, **not** a comprehensive factuality benchmark. All records are fictional and eligibility cannot be inferred from real admission rules. Eligibility filters, seat reservations, counseling policy, updated quota rules and actual round information are deliberately out of scope. Cost: hardware acquisition not included; an illustrative 0.3 kW workstation for 1 hour consumes 0.3 kWh, which costs ₹2.4 at an assumed ₹8/kWh, plus workstation capital and staff/maintenance. Actual consumption and local tariffs vary. No paid LLM API is needed.

## Reproducibility and tools
Source code, CSV, generator, evaluation questions, tests, Docker configuration and README are shipped together. Python, FastAPI, Qdrant, FastEmbed, LM Studio and Qwen are used. AI coding assistance: ChatGPT was used to draft/generate this implementation and documentation; the candidate should review, test and be able to explain all code before submitting.
